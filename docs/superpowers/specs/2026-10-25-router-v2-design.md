# Дизайн: Home Panel — router-v2 (присутствие, телеметрия, управление)

- Дата: 2026-10-25
- Статус: на ревью
- Базируется на: `2026-10-18-homepanel-design.md` (v1, реализован)
- Платформа роутера: Cudy WR3000S v1 — MediaTek MT7981BA (Filogic 820),
  2×Cortex-A53 @1.3 ГГц, 128 МБ flash (NAND), 256 МБ RAM, Wi-Fi 6,
  OpenWrt 25.12.4 (OpenWrt U-Boot layout), ядро 6.12
- Платформа сервера: Debian, Python 3 (только стандартная библиотека)

## 1. Цель

Расширить Home Panel от «кто дома по WiFi» до полного обзора домашней сети:

1. **Мгновенное присутствие** — событие подключения/отключения WiFi доходит до
   панели за секунды, а не за интервал опроса.
2. **Проводные клиенты** — устройства за LAN-портами и bridge видны наравне с
   WiFi, с пометкой типа подключения.
3. **Трафик** — объём принятых/переданных байт по WiFi-клиентам.
4. **Здоровье роутера** — uptime, load average, память, состояние WAN.
5. **Управление** — отключить WiFi-клиента, поставить паузу интернета,
   перезапустить агент.

Ключевые сценарии:

1. Телефон подключился к WiFi → карточка человека на главной обновилась через
   пару секунд, без ожидания 20-секундного цикла.
2. Телевизор подключён кабелем → он виден в списке устройств с бейджем
   «провод», его присутствие учитывается в истории.
3. Роутер перегружен → на главной видно load average и занятую память.
4. Ребёнок засиделся в сети → родитель ставит «Пауза интернета» на его
   устройство; LAN и панель продолжают работать.
5. Устройство зависло в WiFi → кнопка «Отключить от WiFi» сбрасывает сессию.

## 2. Границы

### В рамках

- Агент v2: WiFi + проводные клиенты, телеметрия роутера, трафик WiFi,
  применение команд управления.
- Watcher-сервис на роутере: мгновенная отправка снимка по событиям hostapd.
- Сервер: приём schema 2 (обратная совместимость с schema 1), хранение
  телеметрии/трафика/команд, API управления.
- Веб-панель: карточка роутера, тип подключения, трафик, кнопки управления.
- Обновлённый LuCI-экран: статус watcher и версия агента.

### Вне рамок (YAGNI)

- Полноценная авторизация/пользователи в панели (см. §8 — риск).
- Учёт трафика проводных клиентов (универсального per-MAC счётчика в OpenWrt
  нет; см. §3.6).
- Фильтрация по приложениям/сайтам, родительский контроль по расписанию.
- Управление несколькими роутерами с одного сервера.
- Push-уведомления при закрытой вкладке (остаётся как в v1).
- Замена polling на SSE/WebSocket.
- Блокировка на уровне DHCP/DNS или полный запрет LAN.

## 3. Архитектура

### 3.1. Поток данных

```
OpenWrt
  homepanel-agent (ucode, procd)
    ├── каждые 20 с: WiFi + wired + router + traffic
    └── POST /api/ingest (X-Homepanel-Key)
  homepanel-events (ucode, procd)
    └── ubus listen hostapd.* → debounce 1 с → agent.uc --send

homepanel-server
  ├── parse schema 2 → presence/events/traffic/router_samples
  ├── ответ ingest: control.paused + commands[]
  └── JSON API → браузер
```

Сервер — источник истины для пауз и команд. Агент не хранит состояние между
запусками: при каждом снимке он приводит nft-сет к `control.paused`.

### 3.2. Контракт ingest, schema 2

Запрос `POST /api/ingest`, заголовок `X-Homepanel-Key`.

```json
{
  "schema": 2,
  "agent_hostname": "router",
  "agent_version": "2.0",
  "ts": 1761400000,
  "clients": [
    {
      "mac": "aa:bb:cc:dd:ee:ff",
      "bss": "phy1-ap0",
      "band": "5g",
      "signal": -55,
      "ip": "192.168.1.5",
      "hostname": "phone",
      "connected_at": 1761399000,
      "link": "wifi",
      "rx_bytes": 123456,
      "tx_bytes": 654321
    }
  ],
  "router": {
    "uptime": 864000,
    "load1": 0.3,
    "load5": 0.2,
    "load15": 0.1,
    "mem_total": 262144,
    "mem_free": 131072,
    "wan_up": true,
    "wan_ip": "203.0.113.7"
  },
  "acks": [{"id": 7, "ok": true, "error": null}],
  "errors": []
}
```

Правила валидации:

- `schema` — целое 1 или 2; больше 2 → 400 (`unsupported_schema`).
- `clients` — список; обязателен `mac`. Неизвестные поля игнорируются.
- `link` — `"wifi"` или `"wired"`; отсутствует → `"wifi"` (совместимость с v1).
- `rx_bytes` / `tx_bytes` — неотрицательные целые; отсутствуют → `null`.
- `router` — необязательный объект; числовые поля неотрицательные, иначе 400.
- `acks` — необязательный список `{id, ok, error}`; `id` — целое.
- `errors` — необязательный список строк (ошибки применения control на агенте).
- Снимок schema 1 обрабатывается как раньше, без router/traffic/acks.

Ответ `200`:

```json
{
  "ok": true,
  "ts": 1761400001,
  "clients": 8,
  "arrived": 1,
  "control": {"paused": ["aa:bb:cc:dd:ee:ff"]},
  "commands": [{"id": 8, "type": "kick", "mac": "aa:bb:cc:dd:ee:ff"}],
  "control_errors": []
}
```

- `control.paused` — полный желаемый список MAC на паузе.
- `commands` — команды, которые агент ещё не подтвердил; максимум 20 за ответ.
- `control_errors` — ошибки сервера, которые агент должен показать в логе
  (необязательно).

### 3.3. Команды и подтверждения

Типы команд:

| type      | параметры | действие агента |
|-----------|-----------|-----------------|
| `kick`    | `mac`     | `hostapd.<bss> del_client` для BSS, где MAC ассоциирован |
| `restart` | —         | перезапуск `homepanel-agent` и выход |

Жизненный цикл:

1. Пользователь нажимает кнопку → сервер создаёт `agent_commands` со
   статусом `pending`.
2. Ближайший ingest возвращает команду; сервер ставит `sent` и `sent_ts`.
3. Агент выполняет и присылает `acks` в следующем снимке:
   - `ok: true` → `done`;
   - `ok: false` → `error` с текстом.
4. Если acks нет дольше 60 с после `sent` → `error` («агент не подтвердил»).
5. `restart` не может прислать ack (процесс завершается). Команда считается
   выполненной, если после ответа, в котором она была выдана, пришёл
   следующий валидный ingest от агента (новый процесс). Таймаут — 90 с.

Идемпотентность и защита:

- Повторный `kick` на тот же MAC не создаётся, пока предыдущий `pending/sent`
  моложе 60 с.
- `restart` не создаётся, если уже есть активный `restart`.
- Команда не выполняется агентом дважды: после `sent` она не возвращается,
  пока не истечёт таймаут (тогда `error`, повтора нет).
- История команд хранится 7 дней.

### 3.4. Пауза интернета

- Сервер хранит `device_control(mac, paused, updated_at)`.
- Агент каждый снимок получает полный список `control.paused` и приводит к
  нему nft-сет `paused`.
- nft-таблица создаётся агентом при старте, если её нет:

```
table inet homepanel {
  set paused { type ether_addr; }
  chain forward {
    type filter hook forward priority -150; policy accept;
    ether saddr @paused drop
    ether daddr @paused drop
  }
}
```

- Приоритет `-150` — раньше fw4 (`filter`, priority 0), поэтому drop
  срабатывает до обычных правил.
- Хук `forward` не затрагивает input: DHCP, DNS, доступ к панели и LAN
  остаются рабочими.
- После перезагрузки состояние восстанавливается: сервер снова пришлёт
  актуальный список.
- Если `nft` недоступен или таблицу нельзя создать, агент пишет ошибку в
  `errors` снимка; пауза в UI помечается как «не применена».

### 3.5. Проводные клиенты

- Источники: `bridge fdb show br-lan` (fallback: `brctl showmacs br-lan`) и
  `ip neigh show dev br-lan`.
- Пропускаются записи `self`, `local`, `permanent` на порту CPU и multicast;
  из ARP берутся состояния `REACHABLE`, `STALE`, `DELAY`, `PROBE`.
- MAC, найденный в WiFi-ассоциациях, получает `link: wifi`; остальные —
  `link: wired`.
- IP/hostname берутся из `/tmp/dhcp.leases`. Если устройства нет в leases
  (статический IP), показываются только MAC и `link: wired`.
- Presence-логика сервера не меняется: проводной клиент так же получает
  `arrived` при появлении в снимке и `left` после grace-таймаута.
- **Ограничение:** записи FDB и ARP стареют, поэтому проводное устройство
  без трафика может считаться ушедшим через grace-окно (5 минут). Это
  best-effort присутствие; в UI у устройства остаётся «последний раз виден».
  DHCP-lease не используется как признак присутствия (иначе уехавший ноутбук
  висел бы «дома» до конца аренды).

### 3.6. Трафик

- WiFi: `ubus call iwinfo assoclist '{"device":"<bss>"}'` → `rx_bytes`,
  `tx_bytes` (кумулятивные с момента ассоциации).
- Проводные: универсального per-MAC счётчика нет. В v2 `rx_bytes`/`tx_bytes`
  для них `null`, UI показывает «—». Это осознанное ограничение.
- Сервер считает дельты:
  - хранит последние счётчики в `device_traffic(mac, rx_bytes, tx_bytes, ts)`;
  - при новом снимке `delta = max(0, new - old)`; если `new < old` (сброс
    после переподключения) — `delta = new`;
  - пишет дельту в `traffic_samples(mac, bucket_ts, rx_bytes, tx_bytes)`,
    `bucket_ts = ts // 300 * 300` (5 минут).
- Если `rx_bytes`/`tx_bytes` отсутствуют, счётчики и дельты не обновляются.

### 3.7. Здоровье роутера

Агент собирает:

- `uptime` — `ubus call system info` (`uptime`).
- `mem_total`, `mem_free` — `system info` (`memory.total`, `memory.free`).
- `load1/5/15` — `/proc/loadavg`.
- `wan_up`, `wan_ip` — `ubus call network.interface.wan status` (`up`,
  `ipv4-address[0].address`).
- Модель/прошивка — `ubus call system board` (для LuCI, не для снимка).

Сервер хранит `router_samples` раз в снимок (не чаще раза в 20 с), UI
агрегирует по часам/дням.

### 3.8. Watcher событий

- Новый сервис `homepanel-events` (procd) запускает
  `/usr/share/ucode/homepanel/events.uc`.
- `events.uc` подписывается на `ubus listen hostapd.*`, фильтрует
  `sta_connect` / `sta_disconnect`.
- Дебаунс 1 с (несколько событий подряд → одна отправка), rate-limit не чаще
  одного `--send` в 3 с.
- Запуск: `agent.uc --send` отдельным процессом; ошибки логируются, сервис не
  падает.
- Если `ubus listen` недоступен, watcher завершает работу с понятной ошибкой;
  агент продолжает работать по интервалу 20 с.

## 4. Сервер

### 4.1. Хранилище

Миграции — идемпотентные (`PRAGMA table_info` + `ALTER TABLE`).

Новые поля:

- `devices.link TEXT` (nullable, `wifi`/`wired`).
- `presence.link TEXT`.

Новые таблицы:

```sql
device_control (
  mac TEXT PRIMARY KEY,
  paused INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER
);

agent_commands (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL,
  type TEXT NOT NULL,
  mac TEXT,
  status TEXT NOT NULL DEFAULT 'pending',
  sent_ts INTEGER,
  ack_ts INTEGER,
  error TEXT
);

router_samples (
  ts INTEGER PRIMARY KEY,
  uptime INTEGER,
  load1 REAL, load5 REAL, load15 REAL,
  mem_total INTEGER, mem_free INTEGER,
  wan_up INTEGER,
  wan_ip TEXT
);

traffic_samples (
  mac TEXT NOT NULL,
  bucket_ts INTEGER NOT NULL,
  rx_bytes INTEGER NOT NULL DEFAULT 0,
  tx_bytes INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (mac, bucket_ts)
);

device_traffic (
  mac TEXT PRIMARY KEY,
  rx_bytes INTEGER,
  tx_bytes INTEGER,
  ts INTEGER
);
```

Retention (в `Scheduler.run_once`):

- `router_samples`, `traffic_samples` — 30 дней.
- `agent_commands` — 7 дней.
- `device_control` — не чистится.

### 4.2. API

Существующие эндпоинты расширяются, новые — только для управления.

- `GET /api/state`:
  - каждый элемент `devices[]` получает `link`, `paused`, `rx_bytes`,
    `tx_bytes` (последняя 5-минутная дельта);
  - новый блок `router`:
    ```json
    {"online": true, "last_seen": 1761400000, "uptime": 864000,
     "load1": 0.3, "load5": 0.2, "load15": 0.1,
     "mem_total": 262144, "mem_free": 131072,
     "wan_up": true, "wan_ip": "203.0.113.7"}
    ```
  - новый блок `commands` — последние 10 команд
    `{id, type, mac, status, ts, error}`.
- `GET /api/router/history?days=7` → `{days, samples: [{ts, load1, mem_used, wan_up}]}`
  (агрегация по часам для 7 дней, по дням для 30).
- `GET /api/traffic?mac=...&hours=24` → `{mac, samples: [{ts, rx_bytes, tx_bytes}]}`
  (5-минутные бакеты).
- `POST /api/control/pause` body `{"mac": "...", "paused": true}` →
  `{"mac", "paused"}`. Валидация MAC, `paused` — bool. Пауза разрешена для
  любого валидного MAC, даже если устройства ещё нет в `devices`.
- `POST /api/control/kick` body `{"mac": "..."}` →
  `{"command": {id, type, mac, status}}`.
- `POST /api/control/restart` body `{}` → `{"command": {...}}`.

Все POST-эндпоинты:

- гостю запрещены (существующая проверка «не-GET → 403»);
- возвращают 400 на некорректный MAC/тело;
- не требуют подтверждения на сервере — подтверждение делает UI.

### 4.3. Ingest

- `ingest.py`: `MAX_SCHEMA = 2`; новые dataclass-поля с дефолтами
  (`link="wifi"`, `rx_bytes=None`, `tx_bytes=None`); `Snapshot` получает
  `router`, `acks`, `errors` (все опциональные).
- `App.handle_ingest`:
  1. парсит снимок;
  2. применяет presence как сейчас;
  3. обновляет `link` устройств;
  4. пишет телеметрию/трафик;
  5. обрабатывает `acks`;
  6. завершает `restart`-команды по факту нового ingest;
  7. возвращает `control` + `commands`.
- Ошибка применения control на агенте (`errors`) сохраняется в
  `agent_commands.error` только для команд; для пауз — в лог сервера и в
  `control_errors` следующего ответа (не более одного раза).

## 5. Агент

### 5.1. Сбор снимка

- WiFi: `ubus list 'hostapd.*'` → `get_clients` по каждому BSS, как в v1.
- Трафик WiFi: `ubus call iwinfo assoclist` по BSS; поля `rx_bytes`/`tx_bytes`
  могут отсутствовать — тогда `null`.
- Проводные: `bridge fdb show br-lan`; фильтрация; объединение с WiFi по MAC
  (WiFi приоритетнее).
- DHCP: `/tmp/dhcp.leases` (как в v1).
- Router: `system info`, `/proc/loadavg`, `network.interface.wan status`.
- `agent_version` = `2.0`; `schema` = 2.

### 5.2. Применение управления

- После отправки снимка разобрать ответ:
  - `control.paused` → пересобрать nft-сет (добавить/удалить элементы);
  - `commands` → выполнить по одной, собрать `acks` для следующего снимка.
- Команды выполняются последовательно; ошибка одной не блокирует остальные.
- `kick`: найти BSS по MAC среди текущих клиентов; если не найден —
  `ack {ok: false, error: "клиент не подключён"}`.
- `restart`: `exec("/etc/init.d/homepanel-agent restart")` в отдельном
  процессе, затем выход без ожидания.
- Состояние `acks` хранится в памяти до следующей отправки; при неудачной
  отправке — повтор в следующем цикле.

### 5.3. Конфигурация

Новые ключи UCI (`homepanel`):

- `wired` (bool, по умолчанию `1`) — собирать проводных клиентов.
- `control` (bool, по умолчанию `1`) — применять паузы и команды.
- `events` (bool, по умолчанию `1`) — запускать watcher (используется
  init-скриптом).
- `interval` — без изменений (по умолчанию 20 с).

### 5.4. Установка

- `install.sh` копирует `events.uc`, init-скрипт `homepanel-events`,
  обновляет `agent.uc`, перезапускает оба сервиса.
- LuCI: на странице статуса показывать версию агента, состояние watcher,
  наличие `nft` и ошибку последнего применения control.

## 6. Веб-панель

### 6.1. Главная

- Новая карточка «Роутер»: онлайн/офлайн, uptime, load average, занятая
  память (%), WAN IP и статус.
- Люди и устройства — без изменений; у устройств бейдж «провод»/«WiFi».

### 6.2. Устройства

- Колонка/бейдж типа подключения.
- Для WiFi — мини-график трафика за 24 ч.
- Действия (в раскрытой строке или меню):
  - «Отключить от WiFi» — confirm, POST kick, статус команды;
  - «Пауза интернета» — toggle, POST pause, оптимистичное обновление,
    откат при ошибке;
  - «Перезапустить агент» — confirm, POST restart.
- Статусы команд: «в очереди», «отправлено», «выполнено», «ошибка» с текстом.
- При `router.online === false` кнопки управления disabled с подсказкой.

### 6.3. Аналитика

- Панель «Роутер»: load average и память за 7/30 дней.
- Трафик устройства — в карточке устройства (sparkline).

### 6.4. Гость и TV

- Гость: кнопки скрыты (CSS) и запрещены сервером; блок «Роутер» доступен
  только для чтения.
- TV-режим: в счётчиках учитываются и проводные клиенты.

## 7. Отказоустойчивость

- **Агент недоступен** → `router.online=false`, управление disabled, данные
  показываются с последней отметкой.
- **nft недоступен** → пауза не применяется; UI показывает ошибку, состояние
  на сервере сохраняется (применится, когда nft появится).
- **Сброс счётчиков трафика** → дельта не уходит в минус (см. §3.6).
- **Дубли событий hostapd** → дебаунс + rate-limit.
- **Старый агент v1** → сервер принимает schema 1; команды для него
  истекают с ошибкой, паузы не применяются.
- **Потеря ответа ingest** → агент повторит снимок по интервалу; команда
  останется `sent` и истечёт, повторного выполнения не будет (at-most-once).

## 8. Безопасность

- Ingest — по общему секрету `X-Homepanel-Key`.
- Управление — POST без отдельной аутентификации. **В v1 панель не имеет
  логина, поэтому управлять может любой клиент LAN, не использующий гостевой
  заголовок.** Это ограничение фиксируется явно.
- Гостевой токен — режим просмотра, не граница безопасности: запросы без
  заголовка по-прежнему полноправны.
- Рекомендация при публикации наружу: basic auth на reverse proxy.
- Пауза не блокирует input/LAN/DHCP/DNS — исключена самоблокировка панели.
- Команды идемпотентны, с TTL и защитой от повторов.
- CSRF: аутентификации и cookie нет; сторонний сайт в LAN теоретически может
  отправить POST, но не прочитать ответ. Принятый риск для домашней сети;
  при появлении админ-пароля добавим CSRF-токен.

## 9. Выкат

1. Обновить сервер (schema 2 + API). Старые агенты v1 продолжают работать.
2. Обновить роутер: агент v2 + watcher + LuCI.
3. Проверить чек-лист §11.
4. При откате: вернуть агент v1; сервер совместим.

## 10. Тесты

### Python

- Парсинг schema 1 и 2; отказ при schema 3; `link` по умолчанию.
- Дельта трафика: обычный рост, сброс счётчика, отсутствие полей.
- Команды: создание → `sent` → ack `done`/`error`; таймаут; restart по
  новому ingest; дедупликация.
- Пауза: сохранение, выдача в `control`, снятие.
- Ingest v1 не ломает presence.
- Гость: 403 на все `/api/control/*`.
- Ретеншн: prune телеметрии/трафика/команд.

### ucode

- Фикстуры: WiFi-only, WiFi+wired, DHCP без lease, отсутствие `iwinfo` bytes.
- Применение `control.paused` (мок ubus/nft).
- `acks` для kick (успех/клиент не найден).
- Watcher: фильтрация событий, дебаунс (юнит-тест на функции).

### На роутере (ручной чек-лист)

- `ubus list 'hostapd.*'` и `iwinfo assoclist` с байтами.
- `bridge fdb show br-lan` доступен без root-ошибок.
- `nft` установлен, таблица создаётся, пауза реально режет интернет и не
  режет панель/LAN.
- `kick` отключает телефон, тот переподключается.
- `restart` поднимает агент, сервер видит новый снимок.
- Событие `sta_disconnect` доходит до панели за ≤ 3 с.
- После перезагрузки роутера пауза восстанавливается.
- Проводной клиент виден в панели с `link: wired`.

## 11. Риски и открытые вопросы

- **Байты в `iwinfo assoclist`** зависят от драйвера; при отсутствии полей
  трафик WiFi будет «—». Проверяется на роутере.
- **`bridge fdb`** может требовать прав/пакета; fallback на `brctl`.
- **Проводное присутствие best-effort**: FDB/ARP стареют, устройство без
  трафика может уйти в «офлайн» через grace-окно. DHCP-lease не считается
  присутствием.
- **nft** есть не во всех сборках OpenWrt; пауза деградирует, присутствие
  работает.
- **Wired-трафик** не поддерживается (осознанно).
- **Один роутер** на сервер; мультироутер — вне рамок.
- **Без админ-аутентификации** управление доступно любому в LAN — принято
  для v1, вынесено в §8.
